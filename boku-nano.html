日本語・コード生成の小規模言語モデル

本課題では、日本語の指示からPython関数を生成する小規模言語モデル（SLM）を学習させます。モデルの重みはランダムに初期化します。データ生成、モデルの学習、生成したコードの実行評価までの一連の処理を、6週間で実装します。

01全体構成と課題の目的

Boku-nanoは、「偶数だけを残し、昇順に並べる」のような日本語の指示を受け取り、Python関数のソースコードを出力します。評価プログラムは、生成された関数へリストxsと整数kを渡して実行します。モデルによるコード生成と、Pythonによる生成コードの実行は、別々の処理として実装します。

指示には、語彙と文法を制限した制御自然言語（Controlled Natural Language、CNL）を使います。指示の意味は、「偶数抽出 → 昇順整列」のような操作列で表します。本課題では、操作列を記述するドメイン固有言語（Domain-Specific Language、DSL）を定義します。

受講者は、24種類の操作から1〜4個を選んでDSLの操作列を合成するPythonプログラムを作成します。同じ操作列をCNL生成器とコード生成器へ渡すと、日本語の指示文と正解のPythonソースがそれぞれ得られます。指示文と正解コードを組にして、モデルの学習用データにします。

データを作る

データ生成プログラムは、操作の組み合わせを列挙するか、乱数シードを固定して操作を選び、JSON形式のDSLを作ります。まず仕様を学習用・開発用・評価用データに分割します。次に、同じDSLからCNLと正解コードを別々に生成します。検証プログラムは、CNLを解析して元のDSLを復元できるかを検査します。正解コードは隔離した環境で実行し、実行結果を参照インタプリタの出力と比較します。参照インタプリタは、DSLと具体的な入力から期待値を求めるプログラムです。教師LLMの言い換え候補は、人が意味を確認して辞書へ登録してからCNLの生成に使います。

モデルを学習する

学習用データだけで、文字列をトークン列に変換するトークナイザを作成します。モデルにはランダムに初期化したTransformerを使います。学習時は、CNLと正解コードを連結してモデルに入力し、コードと終了トークン（EOS）の予測だけを損失の計算対象にします。指示の予測は損失の計算対象から除外しますが、コードの予測損失から指示の内部表現にも勾配が伝わります。学習中の設定変更とモデル選択には開発用データを使います。

生成したコードを評価する

最終評価では、学習に使っていない仕様のCNLを学習対象モデルに入力し、コードを生成させます。評価プログラムは、学習用の正解コードと同じ入出力仕様で生成コードを実行し、非公開の入力に対する実行結果を参照インタプリタの出力と比較します。CNLを解析してコード生成器へ渡すルールベース方式とも比較します。比較を通じて、モデルが翻訳規則をどこまで学習し、未知の組み合わせへ適用できるかを調べます。

必修の到達点

第2週までに少数例でデータ生成・学習・コード生成・実行評価を動かします。その後、延べ学習量10Mと100Mなどの比較を行い、学習曲線と失敗例を説明できる状態を目指します。10Mと100Mは、実験計画の基準となる数値です。担当教員は、工程の完成度、検証の妥当性、再現性、比較実験と考察に基づいて成績を判断します。

実行テストによる一致は、有限個の入力についての確認です。すべての入力に対する正しさを証明するものではありません。自由な日本語への対応と大規模なデータ生成は発展課題として扱います。

02問題と操作の定義

生成する関数の名前・引数・戻り値の型（シグネチャ）を、次の定義に固定します。xsは長さ0〜20の整数リストで、入力時の各要素は−100〜100の整数です。kは1〜10の整数です。関数は結果を新しい整数リストとして返し、入力のxsを変更しません。中間値と出力値には、入力時の要素の範囲制限を適用しません。計算にはPythonの任意精度整数を用います。例えば、100を4回二乗すると10**32になります。参照実装では、固定長の64ビット整数で計算してはいけません。

def solve(xs: list[int], k: int) -> list[int]:
    ...

下表の24種類から1〜4個の操作を選び、指定した順に適用します。本課題では、表の各操作を分割しない最小単位（原子的操作）として扱います。各操作は直前の操作結果に作用します。抽出と要素ごとの変換では、残る要素の順序と重複を保ちます。

4操作の例
xsに次の操作を順に適用する。k以上の要素だけを残す。偶数だけを残す。各要素を2倍する。昇順に並べる。結果を返す。
def solve(xs: list[int], k: int) -> list[int]:
    ys = [x for x in xs if x >= k]
    ys = [x for x in ys if x % 2 == 0]
    ys = [x * 2 for x in ys]
    return sorted(ys)

例えばxs = [5, 2, 4, -2, 4]、k = 3なら、結果は[8, 8]です。評価では、生成コードと正解コードの文字列の一致を要求しません。テスト入力に対する実行結果で正誤を判定します。

DSLの形式と24操作

整数リストを扱うDSLの設計と、プログラムを列挙して学習用データを作る方法は、DeepCoderの第4.1〜4.2節と付録Fが参考になります。［19］ DeepCoderは入出力例からプログラムを探す研究です。本課題では、CNLを入力、Pythonソースを出力とする翻訳を学習します。

本課題のDSLでは、仕様をopsだけをキーに持つJSONオブジェクトで保存します。opsの値は、下表の操作名を1〜4個並べた配列です。Pythonで読み込んだ辞書をspecと呼びます。辞書specは、操作列を表す抽象構文木（AST）です。Pythonソースを解析して得るASTとは区別します。

{"ops": ["filter_ge_k", "filter_even", "double", "sort_asc"]}

配列の先頭から順に操作し、同じ操作の繰り返しも許可します。例えば["square", "square"]は二乗を2回行います。kは全操作で同じ値を使い、DSLに具体的な数値は埋め込みません。レコードIDや分割などのメタデータは、DSLの外に保存します。

参照インタプリタとコード生成器は、処理の開始時にDSLを検査します。辞書以外、opsの欠落や余分なキー、配列以外の値、操作数が0個または5個以上、文字列以外の要素、未知の操作名はValueErrorとして拒否してください。検査で型変換や操作の削除は行いません。操作名は下表の識別子として扱い、Pythonの式として評価しないでください。

下表のysは直前の操作の結果、xはysの各要素です。抽出と要素ごとの変換では、要素の順序と重複を保ちます。

参照インタプリタの仕様

interpret(spec, xs, k)は、DSLの操作を直接実行して期待値を返します。DSLを検査した後、xsが長さ0〜20のリストで、各要素が−100〜100の整数、kが1〜10の整数であることを確認します。整数の判定ではboolを除外し、不正な実行入力はValueErrorとして拒否します。

検査後にys = xs[:]で入力をコピーします。spec["ops"]を先頭から読み、操作名に対応する処理でysを更新してください。全操作を終えたらysを返します。入力のspec・xsは変更せず、戻り値は入力リストと別のオブジェクトにします。

参照インタプリタは、入力値の範囲検査を処理の開始時に一度だけ行います。中間値が−100〜100を超えても計算を続け、Pythonの任意精度整数で保持してください。空リストは正常な入力・結果であり、どの操作を適用しても空リストになります。エラーを空リストに置き換えて返してはいけません。

操作の順序や繰り返しはそのまま実行します。次章のデータ分割で使う正規化は、同じグループを見つけるための処理です。元の操作列と分割用の正規形を別々に保存してください。実行時は元の操作列を使い、正規化に基づいて操作を省略しないでください。

コード生成器の仕様

generate_python(spec)はDSLを検査し、solve(xs, k)を一つだけ定義するPythonソースを文字列で返します。生成された関数は、第2章で定義した範囲内のすべての入力に対応します。関数を呼び出すたびに、引数として渡されたxsとkを使って計算します。k = 3などのテスト値や、テスト入力に対する答えをソースに埋め込みません。

初期版の出力形式を固定します。関数定義の次にys = xs[:]を置き、各操作に対してysを更新する文を一つずつ追加します。最後はreturn ysです。例えばfilter_ge_kはys = [x for x in ys if x >= k]、doubleはys = [x * 2 for x in ys]に翻訳します。

コード生成器は、同じDSLから常に同じソースを返し、入力されたDSL自体は変更しません。インデントは半角空白4個、改行はLF、末尾にも改行を一つ付けます。返す文字列にMarkdownのコードフェンス、説明文、関数の呼び出しは含めません。生成した関数は、参照インタプリタや課題側の補助関数、外部の変数に依存せず実行できるようにします。

標準形式では内包表記、スライス、算術・比較、sorted・absを使います。入力の検査は評価プログラムで行い、有効範囲外の入力に対する生成関数の挙動は採点対象にしません。ループなどの等価コードへの展開は、標準形式を検証した後の追加実験にします。out.append(...)を出力する場合は、ローカルなリスト変数へのappend呼び出しを検証器で許可するなど、出力形式と許可構文を対応させてください。

独立した実装として検証する

DSLの型、操作名の一覧、入力の検査器は共有して構いません。操作を実行するロジックと、Pythonの文を出力する規則は別々に実装します。参照インタプリタで生成ソースをexecして期待値を求めたり、生成された関数から参照インタプリタを呼び出したりしてはいけません。参照インタプリタと生成コードが同じ誤りを含むと、結果の比較では誤りを検出できないためです。

まず24操作それぞれについて、入力と手計算した期待値を用意します。参照インタプリタとコード生成器を個別に確認してください。負の奇数、ゼロの倍数判定、重複、空リスト、kがリスト長を超える場合も含めます。例えばxs = [-3, 0, 3, 4]、k = 3にfilter_multiple_kを適用した答えは[-3, 0, 3]です。

次に、操作の順序で答えが変わる例と、同じ操作を繰り返す例を調べます。xs = [2]、k = 3に["double", "filter_ge_k"]を適用すると[4]、逆順では[]です。xs = [100]にsquareを4回適用した答えは[10**32]になります。

各操作、操作の順序、繰り返しの動作を確認した後、同じDSLと入力に対する参照インタプリタの結果と、隔離環境で実行した生成コードの結果を比較します。参照インタプリタと生成コードには、それぞれ独立した入力のコピーを渡してください。戻り値の値と型に加え、入力が変更されていないこと（入力不変性）も検査します。詳細な境界値テスト、ランダム入力、変異テストは第4章に従います。有限個のテストでの一致だけでは、すべての入力に対する正しさを証明できません。

CNLと学習用データを合成する

CNLは、語彙と文法を制限した自然言語です。［2］ 本課題では、日本語の各文を一つの操作に対応させ、文の順序を操作の順序とします。「以上」と「より大きい」、降順整列と逆順などを明確に区別します。

参照インタプリタとコード生成器の動作を確認したら、DSLから日本語の指示文も作ります。実際のデータ生成では、第4章の方法でDSLの仕様を先に分割し、その後に表現を増やしてください。

文法から意味表現と標準的な言い回しの組を作り、その後に言い換えを集める設計は、Wangらの第2〜4節を参照してください。［20］ 同論文は人による言い換えを用いています。本課題では、教師LLMの候補を人が確認して辞書に登録します。

  1. CNLの文法を定義する。 24操作に対応する表現辞書を作ります。教師LLMに各操作の言い換え候補を生成させます。辞書への初回登録時に、受講者が候補の意味と解釈の一意性を確認します。
  2. 表現を増やす。 辞書と文法を使ってCNLを合成します。教師LLMによる文全体の言い換えは、構文解析の結果が一意に定まり、元の操作列を復元できた候補だけを採用します。正解コードは同じDSLからコード生成器で作ります。
  3. 全件を検証する。 次章の検査を通過した指示文とコードの組だけを保存します。仕様・辞書・生成条件を固定した後の大量生成、検査、選別は全自動で実行します。
parseCNL(renderCNL(a))=a

式のaは元の操作列です。辞書内の言い換えは同じ演算子に戻します。未知の表現や複数の解釈がある文は棄却し、例外処理の記録を残します。

本課題のデータ合成は、知識蒸留に着想を得たデータ拡張です。正解コードは規則に基づいて生成し、教師LLMは主に日本語表現を増やします。系列レベルの知識蒸留では、教師モデルが生成した出力系列を学習対象モデルに学習させます。本課題のデータ合成とは、教師モデルの役割が異なります。［1］

04検証とデータ分割

日本語とコードを増やす前に分割する

データ分割の前に操作列を正規化し、同じ仕様から派生するすべての例を一つのグループにまとめます。既知の同値変換によって一致する操作列も、同じグループに含めます。グループ単位で、学習用データ80%、開発用データ10%、評価用データ10%に分割します。例えば、偶数抽出を2回行う仕様と1回行う仕様は、同じ分割に割り当てます。

分割用の乱数シードと各グループの所属を固定してから、言い換えとコード変換を行います。数学的に同値な関数をすべて検出することは要求しません。ただし、採用した正規化規則と、同じ意味の仕様が複数の分割に混入する可能性（データ漏洩）を報告してください。評価用データの内容や評価結果に基づいて、学習用データやモデル設定を修正しないでください。

参照計算にはPythonの任意精度整数を用います。例えば、100を4回二乗した結果は10**32であり、64ビット整数の範囲を超えます。各実行では、戻り値がリストであり、各要素がboolを除くintであることを確認します。戻り値が入力リストとは別のオブジェクトであることと、入力の内容が変更されていないことも確認します。整数の検査にはtype(v) is intなどを使ってください。Pythonではboolがintのサブクラスで、True == 1も成立するため、値の一致だけでは型の誤りを検出できません。［14］

操作列に応じたテストを作る

各例の検証には、境界値を用いたテストと、20件以上のランダム入力を用いたテストを使います。空リスト、長さ1・20、同値要素、重複、負数、全要素が除外される場合、k−1・k・k+1、倍数の前後を含めます。最終評価には、データ生成時の検証とは異なる乱数シードと入力を用います。

比較の境界は、先行する変換を適用した値についても調べます。例えば「2倍してからk以上を残す」仕様では、xs = [2], k = 4の正解は[4]です。比較を誤って>にした実装は[]を返します。元の入力にk−1・k・k+1を含めるだけでは、先行する変換の後で生じる境界条件の誤りを検出できません。操作列を考慮して入力を生成し、失敗時には再現用の乱数シードと具体的な反例を保存します。

テスト自体の品質も検査します。誤った実装を見抜く能力としてテストを評価する考え方は、Maらの第2節を参照してください。［12］ 本課題では、比較演算子の置換、操作の削除、順序の交換によって変異コードを作り、作成したテストが誤りを検出できるか確かめます。変異テストの原理と同値変異の問題は、Jia・Harmanのサーベイを参照してください。［25］

本課題では、別の反例探索によって元の仕様との不一致を確認できた変異の数を、検出率の分母とします。分子は、分母に含めた変異のうち、評価対象のテストが検出した変異の数です。同値だと確認した変異は除外し、同値かどうか未確定の変異は別に件数を報告します。テストで差が見つからなかっただけの変異を、同値と判断しません。

ASTの検査や別プロセス化だけでは実行環境の隔離になりません。権限を制限したコンテナなどを用い、ネットワークやホストのファイルにアクセスできない環境で実行してください。許可リストはsortedやabsなど必要な処理だけを認めます。教員は授業開始前に、動作確認した隔離実行用のひな形と制限値を準備します。

保存する情報

JSONLなどの形式で、レコードID、操作列、グループIDと分割先、CNL、正解コード、テストまたは再現用の乱数シード、各検査結果、コード形式、生成器と辞書の版、教師LLMによる生成の来歴を保存します。指示とコードの両方が一致する組だけを重複として除去します。同じコードに異なる指示が対応する例は、データに残せます。変異の種類、検出結果、確認できた反例も保存してください。

すべてのテストで結果が一致しても、確認できるのは有限個の入力に対する動作だけです。すべての入力に対する正しさを証明するものではありません。参照インタプリタとの共通の誤りを避けるため、独立した実装、手計算の例、境界値テストを組み合わせます。

05データ量とトークナイザ

必修では、小規模コーパスで全工程を完成させてから、延べ学習量10Mと100Mなどの段階的な比較を行います。コーパス量と追加学習の必要性は、開発用データでの評価結果と計算予算から判断します。500M〜1Bトークンの学習用コーパスの構築は発展目標です。10M・100M・500M〜1Bという数値は教材の実験基準であり、本課題の最適値を示すものではありません。

Mは106、Bは109を表します。コーパス量と延べ学習量には、開発用データ、評価用データ、系列長をそろえるための埋め草トークン（パディング、padding）を含めません。学習対象モデルのトークナイザは語彙を固定して使います。固定したトークナイザで、コーパス量と、実際にモデルへ提示した延べ学習量を別々に数えます。

08評価と提出物

SLMの評価では、学習対象モデルだけでCNLからコードを生成します。まず、開発用データに含まれる100以上の仕様グループで、評価処理の動作を確認します。最終評価では、評価用データに含まれる1,000グループ程度を目安とします。確保できるグループ数と計算予算に応じて、最終評価の件数を事前に決めてください。学習中のモデル選択には開発用データを使い、評価用データは最終評価まで保持します。テスト入力や正解コードをプロンプトに含めないでください。

実行による正しさの判定とpass@kの定義は、Chenらの第2.1節を参照してください。［10］ 本課題のpass@1は、貪欲法による1回の生成結果で求めます。pass@5の評価は任意です。pass@5を評価する場合は、各問で5候補を独立に確率的に生成し、1候補以上が合格した問題の割合を報告します。温度（temperature）、top-p、乱数シードも記録してください。同じ貪欲法による生成を5回繰り返しても、pass@5の比較にはなりません。

主評価では、仕様グループごとに事前に固定したCNLを1件ずつ使います。複数の表現を使う評価は別に示し、本章の「仕様ごとに集計し、不確かさを示す」に従って、仕様ごとの平均を求めます。

仕様と表現の変化を分けて測る

表現テンプレート群を学習用と評価専用に事前分割します。まず未学習の仕様を、学習で使ったテンプレートで表現して評価します。次に同じ仕様を評価専用のテンプレートで表現し、同じ実行テストで評価してください。同じ仕様に対する二つの結果を比較して、表現の変化による成績差を調べます。評価専用の表現は、学習対象モデルの学習用データやトークナイザの学習に使いません。

仕様ごとに集計し、不確かさを示す

操作数別の成績と95%信頼区間を報告します。同じ仕様に複数の表現を与えた場合は、まず仕様グループ内で平均し、次にグループ間で平均します。表現数の多い仕様が全体の成績を左右しないようにしてください。信頼区間は、仕様グループを単位として復元抽出するブートストラップ法（bootstrap）などで求めます。言い換え前後の成績差を求める場合は、対応するグループを一緒に再抽出します。表現の違いを独立した問題として数えません。

100問中50問に正解した場合、独立した二項試行を仮定した95%信頼区間は約40〜60%です。評価件数と区間の求め方を示し、点推定の小さな差だけで優劣を判断しないでください。

09自然な日本語への拡張

Boku-nanoは、学習したCNLの範囲内の指示を扱うことを前提とします。自由な日本語を受け付ける応用システムでは、Qwenなど、学習済みの重みが公開されているLLM（オープンウェイトLLM）を前段に配置し、入力をCNLへ変換します。本章では、制約のない自然言語（Uncontrolled Natural Language）をUNLと略記します。

入力 / 自然な日本語
数値の一覧から正の値だけを、小さい順に並べて最初のk個ほしい。
変換後 / CNL
xsに次の操作を順に適用する。正の要素だけを残す。昇順に並べる。先頭からk個を取り出す。結果を返す。

応用システムは、整数データの抽出・変換を行う小規模な前処理機能などに利用できます。システムは変換後のCNLを利用者に表示して、指示が意図に合っているかを確認します。「いい感じに並べて」などの曖昧な要求には、利用者に具体的な指示を求めます。「重複を除く」のような範囲外の要求を、別の処理で代用してはいけません。範囲外の要求にも対応する場合は、DSL・CNL・参照実装・学習用データをまとめて拡張します。

「正の値だけを小さい順に並べて最初のk個を返す」例では[-1, 0, 3, 2, 2]とk = 2から[2, 2]を得ます。「正の値」を「0以上」に変えたり、先に切り出してから並べたりすれば意味が変わります。CNLの構文が正しいことと、元の依頼の意味を保存したことは別に評価してください。

UNL→CNLを学習対象モデルにも学習させる

学習用の仕様から作ったUNLとCNLの組を学習用データに追加し、「UNL→CNL」と「CNL→コード」の多タスク学習を行います。タスク種別はプロンプトで指定します。推論時は同じ学習対象モデルを2回呼び出し、1回目に生成したCNLを2回目の入力にします。この2段階の処理によって、特定の用途で自然な日本語からコードを生成できるかを検証します。

教師LLMが出力したCNLを学習対象にする場合は、出力系列を使う知識蒸留に当たります。UNLとCNLの意味的一致は実行テストだけで確定できないため、独立した注釈者による監査なども必要です。新しい特殊トークンを追加する場合は、語彙・埋め込み・パラメータ数の変更を記録します。

同じ要求集合について、正解CNLを入力するBoku-nano、QwenによるUNL→CNL変換を含むシステム、UNL→CNLを追加学習したモデルを比較します。正解CNLを与える条件は、前段の変換誤りがない参照条件です。未知の日本語表現で、CNL変換の意味正解率とコード実行までの成功率を測ってください。

失敗は「UNLの意味を誤ってCNLへ変換した」「正しいCNLから誤ったコードを生成した」に分けます。曖昧な要求や範囲外の要求について、利用者に確認を求めた件数も別に記録します。追加学習による自然言語理解の改善は、実験で確かめる仮説です。

第8章の必修比較で使うルールベース方式も、同じCNLに対して評価できます。正確さ・速度・メモリを比べ、前段の意味変換と後段のコード生成のどこに改善が必要か考察してください。
